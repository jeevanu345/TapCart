# Optional hosted card payments

Card payment uses the official Stripe Node SDK and hosted Checkout. Card numbers are entered on Stripe's page. Cash-at-desk and the development simulator are separate methods; the simulator is disabled in production. Without configured credentials card payment fails closed with HTTP 503.

Set `STRIPE_SECRET_KEY` (`sk_test_…` for test mode, `sk_live_…` for live mode) and `STRIPE_WEBHOOK_SECRET` (the endpoint's `whsec_…` signing secret). Never commit these values. Run database migrations. Configure a publicly reachable HTTPS endpoint at `/api/payments/stripe/webhook`, using snapshot events for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired` and `checkout.session.async_payment_failed`. Stripe signature verification requires the unmodified raw body, so this route must be mounted with `express.raw({type:'application/json',limit:'256kb'})` before JSON parsing and browser CSRF middleware. The route authenticates Stripe rather than a browser cookie. [Stripe webhook documentation](https://docs.stripe.com/webhooks).

An authenticated customer creates a CARD order with ordinary reservation ownership, versions and idempotency. The customer then requests `/api/orders/{id}/card-payment`; the server must authorize that this is their order. The response contains a hosted URL when payment remains open. A return-page navigation never proves payment. Orders only become paid from a verified signed event or a server-authenticated provider retrieval. [Stripe fulfillment guidance](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page).

The attempt table persists the exact request, stable order-derived provider idempotency key, random attempt identity, session ID and payment-intent ID. Line items use immutable order-unit price snapshots in INR minor units; clients cannot submit an amount, coupon or card settlement result. Metadata binds the provider session to both order and attempt. Webhook processing checks mode, order/attempt metadata, amount, currency, session/intent identity and live/test account mode; event IDs are transactionally deduplicated. A late success can finalize unchanged inventory or create a refund obligation when inventory has moved on.

Hosted sessions expire after 35 minutes, and CARD inventory protection is bounded at 40 minutes. These are policy defaults requiring real shopping/payment observations. Session creation, retrieval and provider retries run outside inventory transactions. The response may be lost after Stripe created the session: retries reuse the persisted request and the same key. Known sessions are retrieved, never replaced. Unknown attempts are not recreated after 23 hours because Stripe's API-v1 idempotency keys may be pruned after 24 hours; such orders require operator/provider reconciliation. A delayed first successful request can also encounter Stripe's session-expiry constraints; preserve the original attempt and resolve it rather than generating another payment. [Stripe idempotency behavior](https://docs.stripe.com/api/idempotent_requests), [Checkout Session API](https://docs.stripe.com/api/checkout/sessions/create).

The worker's `reconcileStripePayments` retrieves known sessions and retries unknown creation responses under the same key while inside the retry window. It checks at most 25 eligible attempts per pass, no more often than once per minute per attempt, and continues past individual failures. It never charges a card itself. Successful events require a completed, paid session and a payment-intent ID. Signature timestamps use the SDK's 300-second tolerance; snapshot event creation timestamps must not be in the future beyond five minutes or older than 31 days. Historical recovery outside that interval uses authenticated retrieval, not an old webhook payload. [Retrieve a Checkout Session](https://docs.stripe.com/api/checkout/sessions/retrieve).

Refund obligations remain visible as REFUND_PENDING with the exact amount due. Authorized staff submit `/api/orders/{id}/card-refund`. The service persists a refund attempt and stable order/generation key, sends the request outside the inventory transaction, and records settlement only from an authenticated Stripe response/retrieval or verified refund webhook. Partial refunds reduce the outstanding obligation without refunding unreturned items. Duplicate delivery/retrieval cannot insert a second refund ledger entry. Lost responses reuse the same immutable amount, payment identity and idempotency key; unknown outcomes beyond 23 hours require provider/operator reconciliation rather than another request identifier.

Add snapshot events `refund.created`, `refund.updated` and `refund.failed` to the webhook endpoint. Only refunds carrying this application's persisted order/attempt metadata affect its ledger. Pending outcomes are retrieved by the worker. Failed refunds stay visible for operator review; a failed/unknown provider result is never reported as money returned. Cash-confirmation routes reject CARD orders. A refund issued manually outside the application needs an audited reconciliation procedure because it does not carry the application attempt identity. Alert on all unresolved obligations and retain provider evidence.

No live provider calls, test-mode network checkouts or actual charges were performed during development. Tests use the real SDK's signature creation/verification and mock only provider API calls; PostgreSQL tests cover lost responses with stable parameters/keys, duplicate successful delivery, amount mismatch a successful late callback after inventory expiry and timeout, and a lost refund response with exact-key replay, ledger deduplication and amount-mismatch rejection. Live/test account access, merchant eligibility, currency/payment-method availability, HTTPS webhook delivery and refund settlement require deployment-specific verification.
